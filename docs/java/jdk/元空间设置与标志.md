## 关键的 JVM 标志

| 标志 | 默认值 | 描述 |
|------|--------|------|
| `UseCompressedClassPointers` | `true` (64位) | 启用压缩类指针，为 Klass 使用 32 位而非 64 位指针 |
| `CompressedClassSpaceSize` | `1G` | 压缩类空间保留大小（上限，不是初始提交量） |
| `CompressedClassSpaceBaseAddress` | `0` | 类空间基址（仅调试，用于测试） |
| `MaxMetaspaceSize` | `unlimited` | 元空间最大提交量（无上限 = 仅受物理内存限制） |
| `MetaspaceSize` | `~21M` | 首次 Metaspace GC 触发阈值 |
| `MaxMetaspaceExpansion` | `~5M` | Metaspace 扩展的最大增量 |
| `MinMetaspaceExpansion` | `~340K` | Metaspace 扩展的最小增量 |

## 提交粒度

Metaspace 内存提交以 64KB 为粒度：

```
虚拟地址空间
┌────┬────┬────┬────┬────┬────┬────┬────┬────┬────┬────┬────┬────┬────┐
│    │    │    │    │    │    │    │    │    │    │    │    │    │    │
└────┴────┴────┴────┴────┴────┴────┴────┴────┴────┴────┴────┴────┴────┘
  64K  64K  64K  64K  64K  64K  64K  64K  64K  64K  64K  64K  64K  64K
  ↑已提交                                                        ↑未提交
```

- `commit_range()` 函数将一个或多个完整的 64KB 粒度从保留状态转为提交状态
- 内存提交是操作系统中唯一消耗物理内存（或交换空间）的操作
- 保留仅消耗虚拟地址空间

## 关键差异：类空间 vs 非类空间

| 特性 | 类空间 (Class Space) | 非类空间 (Non-Class Space) |
|------|---------------------|---------------------------|
| 内容 | Klass 对象 | 其他所有元数据 |
| 保留方式 | `CompressedClassSpaceSize` | 按需扩展 |
| 扩展能力 | 固定，不可扩展 | 可扩展（添加新 VirtualSpaceNode） |
| 64-bit 必要性 | 仅当 UseCompressedClassPointers | 总是存在 |
| VirtualSpaceList | 非可扩展，单节点 | 可扩展，多节点 |
| 地址空间 | 可能零基（便于压缩编码） | 任意地址 |

### 三维评估：64KB 提交粒度

#### 这样实现的好处
- **减少碎片**：过大的提交粒度（如 2MB）会导致大量内存碎片，64KB 是操作系统页大小 (4KB) 的整数倍且足够小
- **位图追踪可行**：64KB 粒度 × 节点大小 64MB = 1024 个 bit，`CommitMask` 可以用 16 个 64 位字表示，操作高效
- **与 OS 页表对齐**：Linux 支持透明大页 (THP) 时，64KB 是多个 4KB 页的组合，提交和回收操作可以合并为更少的系统调用

#### 是否有更好的方案
- **4KB 页粒度**：更为精细，但位图增大 16 倍，内存分配路径上的位操作开销增加
- **2MB 大页粒度**：适合大块提交，但小 Chunk (1K~4K) 场景浪费严重
- **动态粒度**：根据 Chunk 大小使用不同的提交粒度，但实现复杂度大幅增加

#### 不这么实现的问题
- **如果粒度更粗**：小 Chunk 分配时提交过量内存，浪费物理内存
- **如果粒度更细**：提交位图操作变慢，且更多系统调用（操作系统页表修改有最小粒度限制）
