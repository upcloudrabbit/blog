class Settings : public AllStatic {
  // 提交粒度: 64KB (os::vm_page_size 的整数倍)
  static constexpr size_t _commit_granule_bytes = 64 * K;

  // 虚拟空间节点默认大小:
  // 32-bit: 16MB (1 个根块)
  // 64-bit: 64MB (4 个根块)
  static const size_t _virtual_space_node_default_word_size =
      chunklevel::MAX_CHUNK_WORD_SIZE * NOT_LP64(1) LP64_ONLY(4);

  // 虚拟空间节点对齐: 16MB (根块大小)
  static const size_t _virtual_space_node_reserve_alignment_words =
      chunklevel::MAX_CHUNK_WORD_SIZE;

  // 允许在当前位置尝试翻倍 Chunk (buddy 方式)
  static const bool _enlarge_chunks_in_place = true;
};

  • commit_range() 函数将一个或多个完整的 64KB 粒度从保留状态转为提交状态
  • 内存提交是操作系统中唯一消耗物理内存（或交换空间）的操作
  • 保留仅消耗虚拟地址空间

三维评估：64KB 提交粒度

这样实现的好处

  • 减少碎片：过大的提交粒度（如 2MB）会导致大量内存碎片，64KB 是操作系统页大小 (4KB) 的整数倍且足够小
  • 位图追踪可行：64KB 粒度 × 节点大小 64MB = 1024 个 bit，CommitMask 可以用 16 个 64 位字表示，操作高效
  • 与 OS 页表对齐：Linux 支持透明大页 (THP) 时，64KB 是多个 4KB 页的组合，提交和回收操作可以合并为更少的系统调用

是否有更好的方案

  • 4KB 页粒度：更为精细，但位图增大 16 倍，内存分配路径上的位操作开销增加
  • 2MB 大页粒度：适合大块提交，但小 Chunk (1K~4K) 场景浪费严重
  • 动态粒度：根据 Chunk 大小使用不同的提交粒度，但实现复杂度大幅增加

不这么实现的问题

  • 如果粒度更粗：小 Chunk 分配时提交过量内存，浪费物理内存
  • 如果粒度更细：提交位图操作变慢，且更多系统调用（操作系统页表修改有最小粒度限制）
