内核简介

每个处理器在任何指定时间上的活动都无外乎以下三点：

  1. 运行于用户空间，执行用户进程
  2. 运行于内核空间，处于进程上下文，代表某个特定的进程执行
  3. 运行于内核空间，处于终端上下文，与任何进程无关，处理某个特定的中断

以上三种包含所有情况，即使 CPU 空闲时，内核也会运行一个空进程，处于进程上下文，但运行于内核空间

内核阵营

操作系统内核一般分为两个阵营：单内核和微内核（还有外内核，主要用户科研）

  • 单内核：一般以以一整个大的二进制文件存储在磁盘上，单内核运行在单独的地址空间上，将整体作为一个单独的大过程实现，所有的服务都在这个地址空间运行。由于不存在空间（地址）隔离，可以直接相互进行调用，没有通信一说。总体来说实现简单，性能较高，大多数 Unix 采用该方案
  • 微内核：将内核的功能划分为多个独立的过程，每个过程叫做服务器，各自运行在独立的地址空间上。只有对权限比较敏感的服务器才运行在特权模式之下，其它都运行在用户空间。进程间通过 IPC 实现通讯，由于 IPC 机制和 用户空间与特权空间的上下文切换，因此性能不如单内核（理论上）。实际上大多数服务器都运行在特权模式下，因此可直接调用函数进行通信（Windows NT 内核 以及 Mac OS X 内核基于此实现）。但是这违背了微内核的初衷。

进程管理

进程：对于 linux 来说进程就是处于执行期的程序，在 linux 中线程与进程不做特别区分，线程只是特殊的进程。

进程描述符

  • 进程结构体：内核会将进程列表放在任务队列（数据类型为双向链表）中，列表中的每一项都是 task_struct（进程描述符）它包含了一个进程的所有信息，结构体位置（include/linux/sched.h:821）
  • 栈尾新增 thread_info 用于定位 task_struct： Linux 通过 slab 分配器分配 task_struct 结构，为了能够动态且方便计算 task_struct 所在的位置，通过新的 thread_info 结构体定位 task_struct（include/asm-x86_64/thread_info.h:26 以上为 x86 体系下的结构体，其它会有些许不同）
  • PID 最大值：进程的 PID 默认值由操作系统位数决定，默认情况下 32 位机器的最大值是 32768 但也可以通过修改 /proc/sys/kernel/pid_max 来提高上限，但最大上限为 2^29 = 536870912（500 万左右）具体定义（include/linux/threads.h）
/*
* This controls the default maximum pid allocated to a process
*/
#define PID_MAX_DEFAULT (CONFIG_BASE_SMALL ? 0x1000 : 0x8000)
/*
* A maximum of 4 million PIDs should be enough for a while.
* [NOTE: PID/TIDs are limited to 2^29 ~= 500+ million, see futex.h.]
*/
#define PID_MAX_LIMIT (CONFIG_BASE_SMALL ? PAGE_SIZE * 8 : \
(sizeof(long) > 4 ? 4 * 1024 * 1024 : PID_MAX_DEFAULT))
#endif

进程状态

task_struct 中的 state 字段表示进程的状态（-1 unrunnable, 0 runnable, >0 stopped）进程在 Linux 中有 5 种状态：

  1. TASK_RUNNING（运行）—— 进程是可执行的（可能在执行中，也可能在运行队列中等待执行）
  2. TASK_INTERRUPTIBLE（可中断）—— 进程正在睡眠（被阻塞）等待条件达成后内核就会将状态置为 运行，同时发送信号通知进程随时准备运行
  3. TASK_UNINTERRUPTIBLE（不可中断）—— 该状态下与可中断基本一致，但是不响应信号（kill）该状态一般出现在进程必须不受干扰的等待，或者等待的事件马上出现
  4. __TASK_TRACED（被其它进程跟踪的进程）—— 使用 ptrace 调试程序时，被调试的程序状态
  5. __TASK__STOPPED（停止）—— 进程停止执行或者是没有投入执行以及不能执行。一般在收到信号SIGSTOP、SIGTSTP、SIGTTIN、SIGTTOUT 等信号时以及在调试（DEBUG）期间收到任何信号都会进入停止状态

进程创建

  • 进程的创建一般通过 span 机制 —— 在新的地址空间里创建进程，读入可执行文件，最后开始执行。Linux 采用方式不同，它将上述步骤分到两个单独的函数去执行：fork() 和 exec() 。首先 fork() 会拷贝当前进程创建一个子进程，子进程与父进程区别在于 PID 和 PPID（父类进程 ID）以及资源和统计量不同。exec() 函数负责读取可执行文件并将其载入地址空间开始运行
  • Linux 的 fork 采用写时复制技术（copy-on-write）—— 被复制的资源只有在需要写入时才进行实际的拷贝，因此 Linux 的 fork 开销就是分配 PID 以及复制父进程的页表。
  • Linux 通过 clone() 系统调用来实现 fork()，clone 又调用 do_fork() 完成进程的大部分创建任务（kernel/fork.c:1356）。do_fork 又调用 copy_process 完成（就在同文件内）以下为 copy_process 大致流程：
  1. 调用 dup_task_struct 为新进程创建一个内核栈、thread_info 结构和 task_struct，这些值与当前进程完全相同，此时，子进程与父进程的描述符是完全相同的
  2. 检查系统资源（文件最大打开数量，内存，进程数量等）
  3. 开始填充自身信息，与父进程区分开来
  4. 设置子进程的状态为 TASK_UNINTERRUPTIBEL，保证它不会被投入运行
  5. 调用 copy_flags 更新 task_struct 的 flags 成员，超级用户权限标记清零（PF_SUPERRIV），设置进程未被调用标记（PF_FORKNOEXEC）
  6. 调用 alloc_pid 分配一个新的 PID
  7. 根据传递的参数拷贝或者共享打开的文件、文件系统信息、信号处理函数、进程地址空间和命名空间等资源，一般情况下这些资源对于线程都是共享的，对于进程是不同的，因此这里选择拷贝
  8. 最后返回一个指向子进程的指针（成功时，失败会返回指定的特征码）

如果 copy_process 成功返回，一般会立即调用 exec 函数企图执行，内核也会优先调度子进程（这里是因为有写时复制存在，早些调度只需拷贝较少的资源，如果父进程优先执行的话那么有可能让资源变多）优先调度不代表优先执行，实际父进程还是有可能比子进程先执行

线程创建

  • 在 Linux 内核中，进程与线程并不做明显区分，他们对应的结构体都是一样的（task_struct）。唯一区别在于线程的资源都是共享的，线程创建也是通过 fork 实现，只不过需要在参数中传递共享的资源种类（include/linux/sched.h 文件头部就是）
  • 内核线程一般用于内核在后台执行操作，它与普通线程的唯一区别在于其地址空间 mm 指针指向 NULL，它运行在内核空间上，内核线程的创建是通过 kthreadd 内核进程产生（include/linux/kthread.h:7）实际也是调用 clone 实现

进程终结

进程的终结包含资源的释放以及删除进程描述符，进程的终结主要依赖 do_exit 实现（kernel/exit.c），资源的释放如下：

  1. 将 task_struct 中的标志成员设置为 PF_EXITING
  2. 调用 del_timer_sync 删除任一内核定时器。根据返回结果，确保没有定时器排队，也没有定时器处理程序在运行
  3. 如果 BSD 进程记账功能是开启的，那还需调用 acct_update_integrals 来输出记账信息
  4. 调用 exit_mm 函数释放进程占用的 mm_struct，如果没有别的进程使用它们（地址空间没有被共享）就彻底释放
  5. 调用 sem__exit 函数，如果进程排队等候 IPC 信号，则离开的队列
  6. 调用 exit_files、exit_fs，以分别递减文件操作符、文件系统数据的引用计数。如果某个引用计数降为 0 则彻底释放资源
  7. 设置 task_struct 中的 exit_code 为 exit 函数提供的退出代码，或者去完成其它由内核规定的退出动作
  8. 调用 exit_notify 函数向父进程发送信号，给当前要退出进程的子进程重新寻找父进程，新的父进程是线程组中的其它进程或者 init 进程，并把进程状态设置为 EXIT_ZOMBIE（task_struct 中的 exit_code）
  9. 调用 schedule 函数切换到新的进程，当前进程以不再被调度所以需要手动切换
  10. 处于 EXIT_ZOMBIE 状态的进程在父进程检索到信息后，通知内核释放资源

删除进程描述符如下（具体调用 release_task 函数实现）：

  1. 通过调用链：release_task -> __exit_signal -> _unhash_process -> depach_pid 从 pidhash 上删除该进程，同时也要从任务列表中删除该进程
  2. _exit_signal 释放僵死进程的所以剩余资源，并进行统计和记录
  3. 如果这个进程是线程组的最后一个进程，并且领头进程已经死掉，那么 release_task 要通知僵死的领头进程的父进程
  4. release_task 调用 put_task_struct 释放进程内核栈和 thread_info 结构所占的页，并释放 task_struct 所占的 slab 高速缓存

进程调度

Linux 调度采用 CFS 任务调度实现

调度实现

  • CFS 调度的结构体位于 linux/sched.h:1142 行的 sched_entity 结构体中，该结构体被聚合到 task_struct 进程描述符中，名称为 se
  • CFS 使用 vruntime 变量来记录一个程序运行的时间以及它还应该再运行多长时间，vruntime 作为一个 u64 类型的变量，关于它的操作都在 kernel/sched_fair.c#update_curr 中实现。update_curr 计算当前进程的执行时间，并将结果存放在 delta_exec 中，然后调用 __update_curr 对当前可运行的进程总数进行加权计算。最后用算出来的值与当前的 vruntime 相加。update_curr 是由系统计时器周期性调用的，与进程当前所处的状态无关，它不仅能比较精确的计算给定进程的运行时间，还能知道下一个被运行的进程
  • CFS 调度的进程都被放在红黑树的存储结构中，调度时找到 vruntime 最小的那个进程进行调度，也就是 run_node 属性，它是一个 rb_node（红黑树结构）

进程休眠与唤醒

Linux 中进程的休眠和唤醒主要分为以下步骤，休眠：首先进程将自己标记成休眠状态，然后从可执行的红黑树中移除自己，并把自己加到等待队列中，最后再调用 schedule 选择和执行下一个进程。唤醒：进程被设置成可执行状态，然后再从等待队列中移除并加入到可执行红黑树中。

具体的步骤如下：

进程休眠：

  1. 调用宏 DEFINE_WAIT 创建一个等待队列项
  2. 调用 add_wait_queue 把自己加入到（等待）队列中，该队列会在等待的条件达成时唤醒等待的进程，条件的达成主要是由事件触发然后调用 wake_up 唤醒（通常由触发的时间最后调用）
  3. 调用 prepare_to_wait 方法将进程的状态设置为 TASK_INTERRUPTIBLE 或者TASK_UNINTERRUPTIBLE，（再设置一遍的原因是这里要处理经典的伪唤醒问题——即进程还未进入休眠，唤醒的事件已经发生，错过唤醒事件）
  4. 如果等待的事件未发生则把进程状态置为 TASK_RUNNING 与 3 结合共同处理伪唤醒问题
  5. 条件满足后，进程将自己设为 TASK_RUNNING，并调用 finish_wait 方法把自己移出队列

进程唤醒：

  1. 唤醒操作通过 wake_up 函数进行，它会唤醒指定等待队列上的所有进程，内部通过调用 try_to_wake_up 函数实现
  2. try_to_wake_up 函数会将进程设置为 TASK_RUNNING 状态，然后调用 enqueue_task 将进程放入到运行红黑树中
  3. 如果唤醒的进程优先级高于当前正在执行的进程，还要设置 need_resched 标志，通常 wake_up 由触发的事件方最后调用。例如磁盘数据到来时，VFS 就要对其负责的等待队列调用 wake_up 函数

抢占和上下文切换

上下文切换：通常指的是一个可执行进程切换到另一个可执行进程，由定义在 kernel/sched.c#context_switch 方法中，它完成两项基本工作：

  1. 调用申明在 arch/x86/include/asm/mmu_context.h#switch_mm 方法，该方法负责把虚拟内存从上一个进程映射切换到新进程中
  2. 调用声明在 arch/x86/include/asm/system.h#switch_to 方法，该方法负责从上一个进程的处理器状态切换到新进程的处理器状态。（包含保护、恢复堆栈、寄存器信息，还有其它与体系结构相关的状态信息）

用户程序代码能显示的调用 schedule 方法来显示调度下一个进程，除此之外内核也会检查每个进程的 need_resched 标志（thread_info 结构体中）来表明是否需要重新执行一次调度（内核主动切换调度）。当某个进程被抢占、优先级高的进程进入可执行状态、返回用户空间以及从中断返回时，内核都会检查 need_resched 标志，然后调用 schedule 方法切换到新的进程。

抢占主要分为两种：

  1. 用户抢占：主要发生在系统调用返回用户空间以及从中断返回时
  2. 内核抢占：Linux 支持内核抢占（前提是被抢占的进程未持有锁），在 thread_info 中引入 preempt_count 来记录当前进程锁的持有情况（preempt_count 代表锁的数量）。内核抢占主要发生在：中断处理程序正在执行（未返回内核空间）、内核代码再次具有可抢占性时、内核中的任务显示的调用 schedule 方法、内核中的任务阻塞（这里本质还是调用 schedule 方法）

  • 系统调用（也就是 syscall）通常通过 C 库中定义的函数调用进行，调用时可能会产生一些副作用（使系统的状态发生变化）。系统调用通常会返回一个 long 类型的值（负数一般代表失败，0 代表成功），如果发生错误，C 库会把错误码写入全局变量 errno 中（通过调用 perror 库函数可将错误码变成用户理解的错误字符串）

定义系统调用

以 getpid 系统调用为例（它返回当前进程的 pid）

SYSCALL_DEFINE0(getpid)
{
    // 这里返回的是 tgid 也就是组 id，原因是普通进程 ID 和 TGID 相等，
    // 对于线程来说同一线程组的 TGID 都相等，因此这里返回的是 TGID
    return task_tgid_vnr(current);
}
  • SYSCALL_DEFINE0 只是一个宏，它定义了一个无参的系统调用（数字 0 表示参数个数），展开后的代码为 asmlinkage long sys_getpid(void)
  • 系统调用必须添加编译指令 asmlinkage 然后返回值为 long（为了兼容 32 和 64 位系统），其次系统调用在用户空间返回 int 在内核空间才返回 long，最后 getpid 展开后为 sys_getpid 这是 linux 中所有系统都应该遵守的命名规则

系统调用号

  • 在 Linux 系统中，每个系统调用都对应一个系统调用号，进程不会提及系统调用名称而是通过系统调用号进行关联
  • 系统调用号是唯一的，而且分配以后也不允许被替换和回收，而应该通过 sys_ni_syscall 指明这是个无效的系统调用（它返回 -ENOSYS）内核中的系统调用列表（sys_call_table）定义在 arch/x86/kernel/syscall_64.c 文件中

系统调用处理

用户空间的程序无法直接执行内核代码（内核代码运行在受保护的地址空间上）一般通过软中断引发异常促使系统切换到内核态去执行异常处理程序（也就是系统调用，或者叫陷入内核）。在陷入内核前，用户空间程序需要把系统调用号提前放置在 eax 寄存器中。在陷入内核后会自动的从 eax 寄存器中取得系统调用号（去完成对应的系统调用），大多数的系统调用需要提供参数，在传递参数少于 6 个时（不包含 6 个）按照顺序依次填充 ebx、ecx、edx、esi、edi 5 个寄存器，当参数大于等于 6 个时需要用一个单独的寄存器存放指向这些参数在用户空间地址的指针（这种情况比较少见）。系统调用的返回值存放在 eax 寄存器中传递给用户空间

从用户空间访问系统调用

  • Linux 提供的宏名称为 _syscalln 其中 n 从 0 - 6 代表了调用需要的参数，如果不依赖标准的 C 库直接使用系统调用宏，那么应该提供 2 + 2 * n 个参数，例如 open 函数：long open (const char* filename, int flags, int mode)，如果要直接调用：
#define NR_open
_syscall3(long, open, const char*, filename, int, flags, int, mode)
  • 第一个参数为返回类型，第二个参数为系统调用名称，后面的两两组合是参数类型和参数名称。
  • _NR_open 在 arch/x86/include/asm/unistd_64.h 中定义，对应系统调用号。该宏会被扩展成内嵌汇编的 C 函数，将系统调用号和参数压入寄存器并触发软中断来陷入内核。

中断和中断处理

一般来说中断包括硬件中断和软件中断（异常），当硬件中断发生的时候并不考虑与处理器的时钟同步（硬件中断随时可能发生）而软件中断则相反，它必须考虑与处理器的时钟同步

中断处理程序

内核通过执行中断处理程序（也叫中断服务例程 ISR）来响应中断。产生中断的每个设备都应一个中断处理程序（这个程序和中断类型绑定而不是设备绑定）中断处理程序本质就是一个简单的 C 函数，只不过它运行在特殊的中断上下文（也叫原子上下文）中

中断程序的上半部和下半部

对于中断程序而言基本是快和多两个字的集成，为了完成这两个字的需求一般来说中断程序会被分成两部执行，即快速响应硬件设备的上半部和后续处理的下半部，例如：当网卡的有数据包接收时会向内核发出中断，内核立即拷贝网卡数据到内存然后响应网卡，这就是中断的上半部，而下半部对网络包的分析和后续处理则放在下半部执行

下半部主要包含 3 种实现方式：

  1. bottom half（BH）BH 接口提供一个静态创建、由 32 个bottom halves 组成的链表。上半部通过一个 32 整数在中的一位来标识出哪个 bottom halves 可以执行。每个 BH 都会在全局范围内进行同步。即使分属不同的处理器也不允许同时执行
  2. 任务队列，这种实现通过内核提前定义一组队列然后在每个队列都包含一个等待调用的函数组成链表，驱动程序可以把它们自己的下半部注册到合适的队列上去，但是对于一些性能要求高的子系统（网络）无法满足需求
  3. 软中断和 tasklet，在 2.3 版本中内核引入软中断（softirqs），它是一组静态定义的下半部接口，有 32 个，可以在所有的处理器上同时执行（两个相同的也可以）相对于软中断而言的 tasklet 则是易用与性能之间平衡的产物，它可以动态创建，但只能在不同的处理器上同时执行（大多数情况下会使用 tasklet，只有想网络这类对性能要求高的才会考虑使用软中断）
