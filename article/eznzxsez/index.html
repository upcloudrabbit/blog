压缩类指针

约 1368 字大约 5 分钟

重点关注

背景

在 64 位 JVM 中，指针占 8 字节。为了节省内存，JVM 使用压缩指针技术。对于 Java 堆有 -XX:+UseCompressedOops (对象压缩指针)。对于元空间中 Klass 对象的引用，则有 -XX:+UseCompressedClassPointers。

默认情况下，在 64 位平台两者都启用。压缩类指针将 64 位 Klass 指针压缩为 32 位 (narrowKlass)。

假设

  • 所有 Klass 对象都位于类空间的连续内存区域内
  • 类空间大小 ≤ 4GB (32 位窄指针可寻址范围)
  • 如果类空间起始地址为 0 (零基)，则压缩类指针编码更为高效

数据结构

源文件: src/hotspot/share/oops/compressedKlass.hpp

class CompressedKlassPointers : public AllStatic {
  // 编码基址: narrowKlass 解码时加上此值
  static address _base;

  // 编码位移: 窄 Klass 值左移此位数
  static int _shift;

  // 保护区域起始
  static address _protection_zone_start;

  // 保护区域大小
  static size_t _protection_zone_size;
};

编码/解码

// narrowKlass → Klass* (解码)
inline Klass* decode(narrowKlass nk) {
  return (Klass*)((address)_base + ((size_t)nk << _shift));
}

// Klass* → narrowKlass (编码)
inline narrowKlass encode(Klass* k) {
  return (narrowKlass)(((size_t)(address)k - (size_t)_base) >> _shift);
}

偏移模式

支持多种编码模式，取决于类空间的基址和大小：

模式baseshift条件
零基 (Zero)00类空间位于地址 0~4G 内
零基+移位03类空间大小 < 32GB (Klass 8 字节对齐)
非零基非 00类空间不位于零基，但 < 4GB
非零基+移位非 03类空间大小 > 4GB，利用 Klass 对齐

实际上，由于 CompressedClassSpaceSize 默认 1GB，且 JVM 尽可能将类空间映射到低地址，零基模式是最常见的情况。

三维评估：零基+移位模式

这样实现的好处

  • 节省内存：每个对象头中的 klass 指针从 8 字节压缩为 4 字节，以默认堆大小估算可节省 5~10% 内存
  • 零基编码无需加法：base = 0 时解码只需移位操作，无额外加法指令，性能损耗极小
  • Shift=3 利用对齐：所有 Klass 对象 8 字节对齐，低位 3 位始终为零，通过移位编码可覆盖 32GB 地址空间而仍使用 32 位指针

是否有更好的方案

  • 不压缩 (64 位指针)：无需编解码逻辑，性能最佳；但内存开销翻倍，大堆场景不可接受
  • 仅压缩 OOPs 不压缩 Klass：可以减少对象头大小，但压缩类指针节省的内存更直接（每个对象头都有 klass 指针）
  • 使用基址寄存器：部分架构通过段基址寄存器实现零成本压缩（x86-64 的 FS/GS 段），但 HotSpot 未采用

不这么实现的问题

  • 类空间上限 4GB（非移位）或 32GB（移位）：类空间超限时 JVM 启动失败
  • 零基模式依赖 ASLR：操作系统可能无法在低 4G 内分配类空间，回退到非零基模式会增加解码开销
  • 32 位 narrowKlass 溢出：如果 narrowKlass 值超过 0xFFFFFFFF，编码/解码都会出错（但类空间设计保证了不会发生）

初始化

源文件: src/hotspot/share/oops/compressedKlass.cpp

void CompressedKlassPointers::initialize(address base, size_t size) {
  // 确定最优编码参数
  if (base != nullptr && (size_t)base < 32ULL * G) {
    // 零基编码
    _base = 0;
    _shift = 3;  // Klass 8 字节对齐
  } else {
    _base = base;
    _shift = 0;
  }
}

在 Metaspace::global_initialize() 中，类空间保留后立即调用 CompressedKlassPointers::initialize()。

保护区域

当使用零基编码时 (base == rs.base())，JVM 在类空间起始处建立一个保护区域：

CompressedKlassPointers::establish_protection_zone(
    protzone, Settings::commit_granule_bytes());  // 64KB

目的: 如果 Java 代码意外解码一个零值的 narrowKlass ID (即 nk == 0)，解码后试图访问的地址落入保护区域，立即触发 SIGSEGV，而不是稍后在不可预期的地方出错。

布局

类空间布局 (使用 CompressedClassPointers):

┌───────────────────┐  ← base (假设 0x0)
│   保护区域 (64KB)   │  不可访问, 用于捕获零值 nKlass 解引用
├───────────────────┤  ← 第一个可用的 Chunk
│   类 Chunk #1      │
├───────────────────┤
│   类 Chunk #2      │
├───────────────────┤
│   ...             │
├───────────────────┤
│   (未使用)         │
└───────────────────┘  ← base + CompressedClassSpaceSize

保护区域的三维评估

这样实现的好处

  • 故障隔离：零值 klass 解引用从"数据损坏"变为"立即崩溃"，便于定位 bug
  • 低开销：仅 64KB（一个提交粒度），占 CompressedClassSpaceSize (1GB) 的 0.006%
  • 与操作系统协作：借助 OS 的页保护机制，无需 JVM 手动检查

是否有更好的方案

  • 代码中判空：每次解码后检查 null，但引入分支预测开销，对性能影响大
  • 信号处理中输出告警：SIGSEGV 后打印诊断再退出，比直接崩溃更友好
  • 无保护区域：零值解引用访问到已提交内存可能导致静默数据损坏，安全性差

不这么实现的问题

  • 无保护区域时：nk == 0 的解码结果指向类空间起始处，如果是有效内存则静默访问错误数据
  • 调试困难：错误的根本原因（零值 klass）远离最终 crash 点，难以追溯
